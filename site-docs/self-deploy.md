# Self-Deployment & Rollback

KainBain publishes itself, then a human deploys it: a CI stage whose command runs `./publish.sh --detect` (a host command that only ever runs on the backend in the primary checkout) builds and pushes the changed components and writes the release manifest, and `~/apps/kainbain/redeploy.sh` pulls and restarts each component on demand. The legacy `./deploy.sh --prod` path is retired and just prints this pointer. Because a deploy restarts the very service that may have triggered it, the script is hardened for many safe runs per day. KainBain's cross-restart deploy continuity (surviving its own redeploy) lives outside the shared pipeline in `api/continuity/`, enabled only by `KAINBAIN_SELF_DEPLOY_CONTINUITY=1`; generic projects never load it.

- **Self-locating** — `cd`s to its own directory, however it was invoked (even detached by the API).
- **flock lock** — concurrent deploys serialize instead of corrupting the install; a second deploy waits or aborts rather than racing.
- **`.prev` backup** — the live deployment is snapshotted before the swap, so a bad deploy restores atomically.
- **Health gate + auto-rollback** — after restart the script polls `/status`; if the new instance never comes up, it rolls back to `.prev` automatically.
- **Durable state** — status, results, and history live in `~/.kainbain/deploy/` (JSON + JSONL), so the UI reports progress even though the triggering process restarts mid-deploy.
- **Build numbers** — each production deploy consumes the next number from a persisted counter and stamps it into `build.json`; the header shows `#B<number>`.
- **One deploy per stage attempt (continuity plugin)** — the self-deploy continuity plugin stamps a per-attempt `KAINBAIN_DEPLOY_ATTEMPT_ID` into the stage's child environment and re-pins it through the transient-unit re-exec (`systemd-run` does not inherit the caller's environment). The script records it in `~/.kainbain/deploy/attempt-<id>.json` (status, owning pid, timestamps). A re-dispatched deploy stage **adopts** a terminal checkpoint (or waits for a still-running one) instead of running the gates again, and restart reconciliation waits for an in-flight deploy rather than re-dispatching — so one restart mid-deploy can no longer become a `resume → second deploy → restart → …` loop. Inspect `attempt-*.json` and the tail of `deploy.log` when a task reports it is waiting for an in-flight deploy; a checkpoint whose pid is gone falls back to the normal resume path.
- **Stable operation identity (continuity plugin)** — alongside the per-dispatch attempt id, the plugin derives a stable operation key (`merge-deploy:<task>:<branch>:<base-sha>:<cmdhash>`, refined with the task's pre-merge base SHA) and forwards it as `KAINBAIN_DEPLOY_OPERATION_KEY`. Every checkpoint records its `operationKey`, so a re-dispatch that lost its attempt id still joins the recorded attempt for the *same operation* instead of starting a second deploy. A fresh merge (new base SHA) rotates the key, so genuine retries re-run; a recorded failure is never adopted; terminal success adopts only for keys that bind a real base SHA. Adoption is logged as `[DEPLOY] Adopted attempt <id> (<status>) for operation <key>`.
- **Actionable deploy failures (continuity plugin)** — the transient unit's stdio goes to the journal by design, so engine-visible output of a failed deploy is heartbeat lines only. The continuity plugin enriches the failure with the durable records (`last-result.json` → gate name, failed command, log tail) and names the cause under `Deploy cause:`; the parked alert carries `deployGate` / `deployFailedCommand` / `deployAttemptId` (and `projectBlocker` when set). The generic pipeline reports only the ordinary command failure (exit code, stdout, stderr excerpt) and routes to the configured fallback.
- **Shared-gate attribution (continuity plugin)** — the blocking gates (`canary-e2e`, `final-test-suite`) run on the shared workspace, so a gate that is also red on pristine main blocks every task. Evidence is a cached probe for that gate@SHA or, usually, a durable deploy-history record whose `headSha` equals the task's **pre-merge base** and whose failure names the same gate (`last-result.json` / `history.jsonl` now stamp the full `headSha`). With that evidence the continuity plugin classifies the failure as a `project-blocker`: the task parks naming the red branch, its retry budget untouched, one alert per gate@SHA. See the [Red Shared-Gate Runbook](red-shared-gate).
- **Scratch-port drain before the canary gate** — the `canary-e2e` suite provisions its own throwaway stack on dedicated scratch ports (API `:3399`, vite `:5299`). A stack orphaned by a killed or aborted run makes Playwright fail with the opaque `http://localhost:3399/status is already used` error and blocks every later deploy. Before the gate, `deploy.sh` runs `scripts/drain-ports.sh 3399 5299`, which prefers the verified `scripts/canary-preflight.mjs` guard (refuses to terminate a non-scratch occupant) and otherwise reclaims each port through the cross-platform `scripts/free-port.mjs` (SIGTERM, then SIGKILL). The drain is best-effort and never fails the deploy; live services on `:3100` / `:5173` are never touched. See the port-collision section of the [Red Shared-Gate Runbook](red-shared-gate).
- **Hermetic test isolation** — the api suite must never read machine-global state, because the live `~/.kainbain/` files are exactly what a task may mutate. `api/testSetup.isolation.js` (installed as a Vitest `setupFiles` entry) mints per-file temp dirs and pins `PROJECTS_ROOT`, `NOTES_SPACE_ROOT`, `KAINBAIN_CIRCUIT_STATE_FILE`, `KAINBAIN_PROMPT_LAYOUT_DIR`, and `KAINBAIN_CIRCUIT_MEM_ENABLED` *before* any test module imports. This closes the 2026-10-12 leak where a live custom prompt layout that omitted `{{reporting}}` failed the `final-test-suite` gate on one host while CI stayed green. `api/testIsolation.guard.test.js` fails loudly if that wiring ever regresses.
- **Heartbeat ticker & journal stdio** — during long, quiet gates (e.g. test suites, canary, dependency installation), a background ticker refreshes the attempt checkpoint's `updatedAt` (and its owning pid) and touches `deploy.log` every `KAINBAIN_HEARTBEAT_SECONDS` (default 60s) so the continuity plugin's liveness probes stay fresh. The transient unit's stdout/stderr go to the journal by design (no `systemd-run --pipe`): a pipe's reader dies with the API when the deploy restarts the service, and the next write would `EPIPE` the deploy before its terminal result, health gate, and auto-rollback. The journal never has a dead reader, so the post-restart `write_result "success"` always runs; per-gate progress stays in `gate-*.log` and `deploy.log`. Because the unit is silent to the engine, the re-exec keeps the calling shell alive in the background and prints one short progress line to the engine's stdout every `KAINBAIN_ENGINE_HEARTBEAT_SECONDS` (default 30s) until the unit finishes — so the ordinary CI keep-alive heartbeat keeps the stage from being declared stalled. The pump is disposable: a dead engine pipe kills only the pump, never the deploy.
- **Baked changelog** — each production deploy captures the latest 200 commits of the default branch (`master`) into `changelog.json` via `scripts/generate-changelog.mjs`. Production has no `.git`, so baking at deploy time is the only way the app can show its own history. Clicking the header `#B<number>` badge opens it; the `.prev` backup carries the previous changelog, so rollbacks show the matching history.

## Modes and surfaces

```bash
./publish.sh --detect       # publish changed components (build + push + manifest)
./publish.sh --all          # publish every component
cd ~/apps/kainbain
./redeploy.sh --frontend    # pull + restart only the frontend
./redeploy.sh --frontend --tag <previous>   # per-component rollback
./redeploy.sh --all         # pull + restart everything recorded
./deploy.sh --rollback      # legacy: restore the last known-good deployment files
```

Set `KAINBAIN_DOCKERHUB_NAMESPACE` wherever publish runs; a one-time
`./redeploy.sh --init` in `~/apps/kainbain` seeds the release manifest and
the per-component tag keys in `.env` (the legacy single tag key stays).

API: `GET /deploy/status`, `POST /deploy` (`{ fast: true }`), `POST /deploy/rollback`, `GET /deploy/log`, `GET /deploy/changelog?limit=` — the manager spawns detached so it survives the restart. UI: the **Deployment** section in **Settings** with Deploy Now, Fast Deploy, and Rollback. If the changelog dialog says no changelog was baked, redeploy: the artifact only exists from the first deploy that includes the generator step.
