# PR Review — Separate docs repo per project (task 7f6220c3)

Reviewer stage: PR review. Verdict: **PASS** (details at the bottom).

## 1. Does it achieve the goal?

Yes. A project can now keep ALL KainBain information (task docs, plans, reports, and the `.kainbain/` state incl. `project.json`) in a separate private git repo:

- **Opt-in config surface**: `docsRepo: { url, localPath?, branchMode: "synced" }` on the project record, accepted by `POST /projects`, `POST /projects/register`, and `PATCH /projects/:id` (`api/routes/projects.js`). In the UI it appears under a collapsed **Advanced options** disclosure on both the New Project and Add Existing Project dialogs (`frontend/src/components/layout/Header.jsx` + new `DocsRepoFields.jsx`), and in Project Settings → Files & Repositories (`PathsAndReposSection.jsx`, `ProjectSettingsForm.jsx`) for enable/disable later. Matches survey q2 (Advanced section) and the task text ("allowed from the default when you import/create").
- **Stealth (q5)**: with `docsRepo` set, nothing KainBain-related is written into the main repo — `createProject` skips the `.gitignore` write and the docs symlink (`api/projectStore.js:978,1020`), `ensureDocsLink` returns `external-docs` and never touches `<cwd>/docs` (`api/projectStore.js:1523`), `_migrateDocsLink` is skipped (`api/projectStore.js:2082`), and the pointer map (`docs-repo-pointers.json`) lives engine-globally next to the projects registry, never in the main repo (`api/project/docsRepoPointer.js`). Guards: `assertDocsRepoSeparateFromMain` 400s when `localPath` is inside the main repo or `url` equals the main remote; `_assertDocsRepoUnclaimed` 409s when another project claims the same URL/path (q7: one per project). All covered by tests in `api/routes/projects.docsRepo.test.js` (incl. "keeps the main repo clean" and "writes nothing KainBain into it").
- **Single seam**: `resolveKainbainHome(cwd, project)` (`api/project/resolveKainbainHome.js`) maps docs/state resolution onto `docsRepo.localPath` when set, else `cwd`. `resolveDocsPath`, `resolveKainbainDir` and everything derived from them (`resolveTasksDir`, `resolveTaskDocsDir`, `resolveSessionsDir`, `resolveWorktreesDir`, `resolveQuarantineDir`, `resolveProjectConfigPath`, `reportRelPath`) chain through it. `promptCuration.js` was fixed to route through `resolveTaskDocsDir` instead of hand-building `<cwd>/docs/...`. Legacy projects (no `docsRepo`) are byte-identical — proven by `api/docsRepoResolution.test.js`.
- **Runners (the core ask)**: `prepareWorkdir` grows `docsRepoUrl`/`docsLocalPath` and prepares a paired docs worktree `<workRoot>/kb-<taskId>-docs` on the SAME `kb/<taskId>` branch from its own mirror (clone mode) or adopted checkout (`runner/project.js`). The pair counts as one `WORKTREE_CAP` slot; `listOrphanWorkdirs` hides the `-docs` twin and eviction/reap treat the pair atomically. The claim payload carries the redacted `docsRepoUrl` (`api/flow/runnerRoutes.js`), so remote runners can clone both. `shouldSyncTaskDocs` skips the primary→worktree docs copy when the docs worktree exists (docs already live there via git); `collectTaskFiles` and `KAINBAIN_TASK_DOCS` read from the docs worktree; `applyBackendPrompt` retargets backend-curated docs paths to the runner's docs worktree (docs-home rewrite first, to avoid the `<cwd>-kainbain-docs` prefix trap); `commitAndPush` commits+pushes the docs worktree FIRST and labels failures `docs repo (...)` before any code push (`runner/gitOps.js`). Real-git integration tests cover clone mode, adopt mode, same-URL refusal, docs-first push order, and docs-failure-aborts-code-push (`runner/project.docsRepo.test.js`).
- **Auth (q3)**: same login as the main repo (ambient git credentials); stored URL is credential-redacted at write and re-redacted on read/exposure (`normalizeDocsRepoSettings`, `docsRepoUrlFor`, `assertValidDocsRepoForWrite`). Matches the survey answer; no new secret surface.

## 2. Did it follow the plan?

Mostly yes. Phase 1's "make change easy" seam (`resolveKainbainHome`) landed exactly as designed (D1), the validation scaffolding (D4) is strict-on-write/tolerant-on-read with `INVALID_DOCS_REPO_*` codes like the existing docsDirName pattern, and the runner seam prep (D5) exists (`docsWorkdirFor`, `shouldSyncTaskDocs`). Two documented deviations from the plan/survey, both surfaced in `site-docs/separate-docs-repo.md` as v1 limitations:

1. **q4 (existing docs on switch-on)**: survey answer was "Ask me each time"; the implementation leaves old docs in place and only new work goes to the docs repo, with a documented manual move procedure (the plan's ★ recommendation). No per-time prompt exists. Safe and reversible; flagging so the requester can confirm this matches intent.
2. **B5 (merge stage)**: docs `kb/*` branches are created/pushed synced but NOT auto-merged at the merge stage in v1 — explicitly documented in the site-docs limitations. Code merge semantics unchanged.
