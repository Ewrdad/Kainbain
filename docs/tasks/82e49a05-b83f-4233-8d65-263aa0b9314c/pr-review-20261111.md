## Blocking 1: the published runner tarball layout broke remote installers

`scripts/package-runner.sh` now emits the `package-runner.mjs` layout:
`kainbain-runner-<v>-<plat>-<arch>/{runner,api,shared,version.json,INSTALL.txt}`.
There is no top-level `runner/` directory and no `startRunner.sh`.
I verified this by running `node scripts/package-runner.mjs --platform linux --arch x64 --version 0.1.0 --out <tmp>`.
`startRunner.sh` appears 0 times in the archive.

publish.sh still records this file as `components.runner.artifact` (`kainbain-runner-<short>.tar.gz`) in
`dist/release-manifest.json`. These consumers are unchanged and still expect the old layout
(`runner/runner/main.js` plus `startRunner.sh` at the archive root):

- `deploy/install-runner.sh:149-153`: `mv "$tmp/runner" …; cp "$tmp/startRunner.sh" …`
- `deploy/install.sh:319-320`: same pattern
- `deploy/redeploy.sh:228-232`: same pattern
- `kainbain-addsite/Kainbain-adsite/public/{install-runner.sh,redeploy.sh}`: same pattern

With this change, every one of these fails on fresh remote installs and on redeploys, which is the remote-runner
path this task is meant to fix. The new conformance test only checks the archive against `applyUpdate`, so it
does not catch this.

The new wrapper create path in `startRunner.sh` also sources `$PWD/scripts/lib/runner-install-root.sh`. Only
`deploy.sh --prod` ships that file next to `startRunner.sh`. The tarball-based installers do not ship it, so
`startRunner.sh --id …` breaks for them even with the old layout.

## Blocking 2: direct-entrypoint hosts loop silently and report false success

Hosts that have not been migrated still run `ExecStart=node main.js`. Today that includes server2-alpha,
local-alpha and local-bravo. On those hosts:

1. `maybeSelfUpdate` stages the release and the daemon exits 0.
2. systemd restarts the old directory.
3. `joinAndHeartbeat` calls `markUpdateSuccess({ version: RUNNER_VERSION })` without comparing it to `state.to`,
   so it logs "Runner update to 0.1.0 booted … (marked success)".
4. `handlePendingCommands` acks the request with "updated to X".

The new backend auto-nudge (`shouldAutoRequestUpdate`, daily) and the hourly idle check then repeat this
forever. That is the original "server2 says out of date" symptom, now with a misleading success ack. It goes
against survey q8 ("failed update keeps old version + clear error"). The doctor detects the problem, but only
when someone runs it by hand.

## Fix guidance

1. Keep the old layout for the publish/deploy tarball (`runner/{runner,api,shared}` + `startRunner.sh` +
   `scripts/lib/runner-install-root.sh`), or update every `deploy/*` and addsite consumer in the same change.
   Add a conformance test that extracts the publish tarball and runs the real `deploy/install-runner.sh`
   extract step (or an equivalent layout assertion) against it.
2. At runtime, refuse to apply when the process is not running from `<installRoot>/current`. Compare
   `realpath(process.argv[1])` with `realpath(installRoot/current/runner/main.js)`, or have the wrapper export
   a marker such as `KAINBAIN_RUNNER_WRAPPER=1`. In that case, report `updateStatus {state:'failed',
   reason:'direct entrypoint — run scripts/migrate-runner-to-wrapper.sh'}` and a failed `requestUpdate` ack.
3. Only call `markUpdateSuccess` when `RUNNER_VERSION === state.to`. Otherwise record a failed or mismatch status.
4. Add tests for points 2 and 3.
