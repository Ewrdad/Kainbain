# Frameworks for Kainbain Auditability

To ensure that Kainbain can be safely used by organizations in compliance-oriented development, the auditability framework must move beyond simple logs to a system of **verifiable evidence**. 

Depending on the target industry and the level of trust required, the following industry-standard frameworks and technical patterns should be used as the basis for the audit design.

## 1. Compliance & Governance Frameworks
These frameworks provide the "What" and "Why" of the audit trail (the requirements).

### SOC 2 (System and Organization Controls 2)
- **Relevance:** The gold standard for service providers managing customer data.
- **Application to Kainbain:** 
    - **Common Criteria (CC):** Focus on "Change Management" and "System Operations."
    - **Requirement:** Evidence that every change to the codebase was requested, approved, tested, and reviewed.
    - **Audit Goal:** Create a direct, immutable link between a user request (Intent Survey) $\rightarrow$ AI plan $\rightarrow$ implemented code $\rightarrow$ verified test result $\rightarrow$ human sign-off.

### ISO/IEC 27001 (Information Security Management)
- **Relevance:** International standard for information security.
- **Application to Kainbain:** 
    - **Annex A.12.1.2 (Change Management):** Requires that changes to the organization's information processing facilities and systems are controlled.
    - **Audit Goal:** Verifiable history of who (human or agent) changed what, when, and who authorized it.

### NIST AI Risk Management Framework (AI RMF)
- **Relevance:** Specifically designed for managing risks associated with AI systems.
- **Application to Kainbain:** 
    - **Govern & Map functions:** Requires documenting the AI's role in the workflow to ensure accountability.
    - **Audit Goal:** Transparency of model identity, versioning, and the exact prompts used to generate code, to detect and trace "AI hallucinations" or biased logic.

## 2. Technical Trust & Verifiability Patterns
These patterns provide the "How" (the implementation) to ensure the history is trusted.

### SLSA (Supply-chain Levels for Software Artifacts)
- **Relevance:** A security framework for software supply chains to prevent tampering.
- **Application to Kainbain:** 
    - **Provenance:** Every artifact (a code commit or a stage report) should have an associated provenance record.
    - **Non-falsifiability:** The audit trail must be generated by a trusted builder (the Runner) and signed, so an agent cannot "lie" about having run a test.
    - **Audit Goal:** Transition from "text files in a folder" to "signed attestations" (e.g., using in-toto).

### IETF RFC 6962 (Certificate Transparency / Merkle Trees)
- **Relevance:** Used to make logs public and immutable.
- **Application to Kainbain:** 
    - **Append-only logs:** If the organization requires high-trust, the audit history should be stored in a Merkle-tree based ledger.
    - **Audit Goal:** Provide "Proof of Inclusion"—the ability to prove that a specific stage result existed at a certain time and has not been altered since.

---

## 3. Auditor's Guidance: Mapping Frameworks to Kainbain Components

When auditing the current and future state of Kainbain, the auditor should check for the following mappings:

| Kainbain Component | Framework Requirement | Audit Evidence Required |
| :--- | :--- | :--- |
| **Intent Survey** | SOC 2 / ISO 27001 | Timestamped record of user requirements and constraints. |
| **Agent Planning** | NIST AI RMF | Exact prompt $\rightarrow$ model version $\rightarrow$ planned output. |
| **Stage Execution** | SLSA / SOC 2 | Cryptographically signed result from the Runner. |
| **CI/Test Results** | SOC 2 | Immutable link between the code version and the test pass/fail event. |
| **Human Approval** | ISO 27001 / SOC 2 | Digital signature or verifiable identity log of the approving human. |
| **Audit History** | RFC 6962 / SLSA | Hash-chained log or signed bundle that prevents post-facto modification. |
