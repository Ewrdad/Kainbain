# Upgrade-safety review — Restart / Update split + per-runner desiredVersion

**Stage goal:** verify the current change as implemented will not break existing installs on update. If it would, fail the stage (do not fix).

**Branch evaluated:** `kb/78e0522a-430d-4659-9e2f-7db6444d13f9` diff `main...HEAD` (33 files, incl. `api/flow/runnerRegistry.js`, `api/flow/runnerVersionCompat.js`, `runner/daemon.js`, `runner/updates/index.js`, `runner/updates/state.js`, `runner/bin/kainbain-runner`, `frontend/src/components/settings/runnerConfigHelpers.js`, `frontend/src/components/settings/RunnerConfigurationSection.jsx`).

## Method
Read every changed file on `HEAD` against `main`, plus `scripts/lib/runner-install-root.sh`, `scripts/install-local-runner.sh`, `scripts/migrate-runner-to-wrapper.sh`, `scripts/package-runner.mjs`, and the persisted-state loaders (`api/flow/runnerRegistry.js::_loadState`, `runner/updates/state.js::readUpdateState`). Checked both rollout directions: (a) old installs self-updating to the new code, (b) mixed fleet (new backend ↔ old runner, old backend ↔ new runner, new frontend ↔ old backend).

## Backward-compatibility properties verified

### 1. Backend persisted state — additive, lenient load, no version bump
- `RUNNER_STATE_VERSION` stays `3`. `_loadState`/`_persist` call `normalizeOperatorConfig` unconditionally. New field `desiredVersion` defaults to `"latest"` in `defaultOperatorConfig` and is normalized via `normalizeDesiredVersion(raw.desiredVersion ?? "latest")`. Test `old state predating desiredVersion backfills to latest` (`api/flow/runnerRegistry.test.js`) writes a v3 file without the field (operatorConfig `{ displayName: null }`) and asserts both `desiredVersion` and `operatorConfig.desiredVersion` read `"latest"` after load.
- `normalizeDesiredVersion` (`api/flow/runnerVersionCompat.js`) is lenient on STORE: `null`/`undefined`/`""`/`"latest"`(any case) → `"latest"`; version-like strings coerce via `coerceRunnerVersion`; anything else falls back to `"latest"` — never stranded on an undeployable value. Strictness lives only on `PATCH` (`updateConfig` throws `400 INVALID_DESIRED_VERSION` for malformed strings/non-strings), so a hand-edited state file cannot brick the registry.
- `normalizePendingCommands`/`normalizeCommandResults` filter by `RUNNER_COMMANDS.includes(command)`. Upgrading is safe (old entries are a subset of the new three). Downgrading past a queued `requestRestart` drops that one command — at-most-once semantics, not a fleet brick.
- `updateConfig` whitelist adds `"desiredVersion"`; the `next` copy seeds `desiredVersion: current.desiredVersion ?? "latest"` so PATCHes that omit the field (the only shape old frontends send) preserve the setting instead of resetting it.
- `_public` is additive: `desiredVersion`, `availableVersions`, `update.desiredVersion` are new keys; no existing key is renamed/removed. `fleetKnownVersions` is pure, offline-safe (unions runner-reported versions + `recommended`/`minimum` knobs, `coerceRunnerVersion`-filtered, capped 30) and cannot throw on junk records.

### 2. Old runner ↔ new backend
- Old daemon advertises `["requestModelRediscovery","requestUpdate"]` and ignores unknown commands (`handlePendingCommands` `continue`s). New backend's `enqueueCommand` never gates on advertised commands (pre-existing behaviour), but the UI gates on `commands.supported` (`canRequestRestart` in `runnerConfigHelpers.js` requires `requestRestart` in `facts.commands`), so operators see a disabled Restart with "too old — update the Runner" guidance instead of a dead button. A queued `requestRestart` for a pre-feature runner simply sits until TTL (`24h`) and expires as a failed ack — no crash, no workflow interruption, R1 pattern preserved.
- `updateDirectiveFromBeat` on old runners returns only three keys; new directive adds `desiredVersion: null`. Old runners ignore the new field (their `updateDirectiveFromBeat` predates it). Compat-gated selection therefore behaves exactly as before.
- `shouldAutoRequestUpdate` gains `desiredVersion` param gated by `isPinnedDesiredVersion(desiredVersion ?? DESIRED_VERSION_LATEST)`. Old runners have no pin (default `"latest"`), so the daily auto-nudge behaviour is unchanged: at most one pending, daily cooldown, idle-only apply retained.

### 3. New runner ↔ old backend
- `updateDirectiveFromBeat` reads `desiredVersion` via `pick(update.desiredVersion)` → `null` when the backend omits it. `pinnedDesiredVersion` maps `null`/`"latest"`(any case)/`""`/non-string/junk → `null` (fail-open to latest-tracking, today's behaviour). `maybeSelfUpdate` only skips auto-checks when `effectiveTarget` is a valid pinned string, so old-backend runners keep the hourly idle check + 409-triggered path unchanged. Verified by `pinnedDesiredVersion` and `maybeSelfUpdate` unit tests (`runner/daemon.test.js`: `pinnedDesiredVersion({ desiredVersion: "bogus" }) => null`; heartbeat cases carry `desiredVersion: null`).
- `SUPPORTED_RUNNER_COMMANDS` and `support` filtering are additive. An old backend returns `supported` without `requestRestart` (its `RUNNER_COMMANDS` has two entries), so the new frontend renders Restart disabled — never a broken action.

### 4. Runner self-update — default-path unchanged, new path fail-closed and downgrade-proof
- `checkForUpdate` gains `targetVersion = null` default. `checkGithubForUpdate`/`checkMirrorForUpdate`/`checkSingleMirrorManifest` take `targetVersion` through and branch only when truthy; when `null` every pre-filter is the old expression (`isNewerVersion`, `isPrereleaseVersion` skip, compat filter). The pinned pre-checks (`isValidVersion`, `compareVersions` order `-1`/`0`/`null`) short-circuit before any network when `targetVersion` is set, so junk pins fail loud (`ok:false`, reason string) and never install.
- Pinned install constraints: `compareVersions(target, current) === 0` → `ok:true, update:null, reason:"already on pinned"` (no-op); `-1` → `ok:false, reason:"never downgrades"`; `null` → `ok:false, reason:"cannot compare"`. Mirror/GitHub list walks match `compareVersions(tag, target) === 0` only, never a newer substitute. `checkSingleMirrorManifest` requires the served manifest version to equal the pin. These satisfy ADR 0012 "never downgrade" and "verified, compat-filtered" invariants; a pinned runner therefore cannot silently jump over its pin nor strand below the fleet floor (floor still 409s, UI disables Update with `pinBlocksUpdateReason`).
- `maybeSelfUpdate` with a pin and `!force` returns `{ checked:false, reason:"pinned to X: manual update only" }` without touching the network. Manual `requestUpdate` (force) passes the pin through as `targetVersion`. Indistinguishable from the old path when no pin is present.

### 5. Same-tree Restart reboot — sentinel is best-effort; shutdown is not breakage
- New daemon `requestRestart` handler: stage ack → confirm heartbeat (best-effort, warned on failure) → `requestWrapperRestart({ installRoot: installRootFor(config) })` in try/catch (warns `sentinel not written`) → `process.exit(0)`. The `try/catch` + warn makes an unwritable/missing install root degrade to a plain exit, never a crash. An unwrapped `node main.js` host therefore just exits (as documented) instead of erroring.
- Wrapper (`runner/bin/kainbain-runner`) change: only the `AFTER === BEFORE` branch gains `if [ -f "$INSTALL_ROOT/restart-requested" ]; then rm -f …; RESTARTS++; sleep 2; continue; fi`. Normal completion (single-assignment done / idle-out, no sentinel, no `current` flip) still `exit 0`s directly. A staged update still re-execs via the existing `AFTER != BEFORE` branch. Non-zero daemon exits still propagate with no loop. Stale sentinel safety: `rm -f` before re-exec + the shared `RESTARTS > 50` cap guarantees at most one extra boot, never a loop (both covered in `runner/updates-wrapper.test.js`).
- `requestWrapperRestart` creates the install root recursively and writes `{ pid, at }` JSON. It does not touch `update-state.json` (`readUpdateState` still reports `"idle"` in tests), so the failed-boot rollback gate (`bootstrapUpdateState`, `MAX_BOOT_ATTEMPTS = 3`) is unaffected. A sentinel left by a crash between write and exit is consumed by the same restart counter, not by the boot-attempt gate.
- Existing installs self-updating: `applyUpdate` flips `current`/`previous` and leaves `$INSTALL_ROOT/bin/kainbain-runner` as a stable shim copy. The extracted new tree *contains* the sentinel-aware wrapper but the shim is not refreshed by `applyUpdate`. The old shim still re-execs on `current` flips (old update behaviour intact). The sentinel from the new daemon is ignored by the old shim (no match, plain `exit 0`); systemd units in this repo use `Restart=always` (`scripts/install-local-runner.sh`, `startRunner.sh`), so the reboot strength is unchanged. No install is stranded without a running daemon; the worst case is the new Restart feature degrading to a systemd restart until the shim is re-laid by `install-local-runner`/`migrate-runner-to-wrapper` (both already copy `runner/bin/kainbain-runner` to `$INSTALL_ROOT/bin/kainbain-runner`). This is a feature staleness gap, not a break of existing update/heartbeat/dispatch behaviour.

### 6. Frontend / API — dual-read fallbacks, no breaking contract change
- `resolveDesiredVersion` falls back `desiredVersion ?? operatorConfig.desiredVersion ?? update.desiredVersion ?? "latest"`; `normalizeDesiredVersion` trims and case-folds. Old backends return `undefined`/`""` for the new keys, which read `"latest"` — the version selector renders "Latest (recommended)" and `versionWarningForRunner` for a latest-runner compares `compareRunnerVersions(running, recommended)`.
- `versionOptions` unions `selected.availableVersions ?? []`, `recommendedVersion`, `runningVersion`, and the stored pin, then sorts via `compareRunnerVersions(b, a) ?? 0`, so the current selection is always renderable even when the backend list is empty (offline/regression path). `compareRunnerVersions` returns `null` for unparseable inputs and every caller treats `null` as "cannot prove a difference" — warnings stay quiet on junk instead of scaring.
- `Reload` is preserved as a demoted text button (`data-testid=runner-reload-<id>`, `title="Reload configuration from backend"`). *Restart* is a new separate destructive button with `role="alertdialog"` confirmation (`runner-restart-modal-<id>`, names the runner, warns running work will be stopped, shows current task id when busy). Breaking nothing that existed; `reloadSelected` still re-reads config.
- `domainRegistry` and `runnerRequests` add one operation (`requestRunnerRestart`, `POST /runners/:id/commands { command: "requestRestart" }`) and no operation is removed/renamed. The previous CI failures (`api.surface.test.js`, `domainRequests.test.js` pinning exact key lists) were updated to include the new key; the full frontend suite passes on this branch.

### 7. What was *not* changed
- No new required env vars, no config-schema migration, no `RUNNER_STATE_VERSION` bump, no protocol bump (`RUNNER_PROTOCOL = "v1"` unchanged), no `KAINBAIN_RUNNER_MIN_VERSION` / `KAINBAIN_RUNNER_RECOMMENDED_VERSION` semantics change, no runner-bytes-via-backend (R05 stands; Amendment 2 touches only the *directive*), no Windows/pre-release policy change.
- `api/flow/runnerRoutes.js` is untouched by the branch (`git diff` null) — the only backend file in the diff is `api/flow/runnerRegistry.js` plus compat helpers. `runner/updates/state.js` only adds `RESTART_REQUEST_FILE` + `requestWrapperRestart`; `readUpdateState`/`writeUpdateState`/`acquireUpdateLock`/`bootstrapUpdateState` semantics unchanged.

## Verdict
No clause of the change breaks an existing install on update. Every rollout direction was verified against actual loader/dispatch code and existing tests: old state backfills, old runners ignore or disable the new command, new runners read old directives as latest, pinned installs fail closed without downgrading, and the Restart sentinel degrades to a systemd restart rather than stranding a runner. The sole soft spot — `$INSTALL_ROOT/bin/kainbain-runner` not being refreshed by `applyUpdate` — leaves the reboot strength intact via `Restart=always` and is already the documented shim-refresh path through the installers, not a fleet break.
