# Goal
# Decision (approved in architecture discussion, 2026-10-31)

Adopt **Option A: an external, versioned artifact store as the runner update channel** — specifically **GitHub Releases** (repo is migrating to github.com/Ewrdad/Kainbain; release assets on a public repo have no bandwidth limit and cost $0) or **Cloudflare R2** (10 GB free, $0 egress) if the S3 API is preferred. **Do NOT** ship runner code from the backend (rejected Option B).

Rationale, tied to the risk register in `docs/../MuseCodeHackathon2026/Portability/RiskAssessment.md`:
- **R05 (backend→runner code execution supply chain)**: the backend already curates prompts/skills that runners execute; if it also distributed runner binaries, one backend compromise = silent RCE on every runner host. Keeping the artifact channel external and signature-verified keeps that blast radius capped.
- **R03 (backend SPOF, accepted)**: pull-based updates keep working while the backend is down.
- **R11 (version/protocol skew)**: backend still does the version handshake at register/heartbeat, shows the fleet version matrix in the UI, flags 'update available', and **refuses dispatch to runners outside the compatibility window** — that enforcement is what actually closes R11.
- **Cost (hobby project, ~10–20 runners, ~50 MB binary × 6 platform artifacts ≈ 300 MB/release, monthly releases, keep 10)**: GitHub Releases = $0 (no bandwidth cap on public repos, Actions free on public repos); R2 = $0 (10 GB free storage, egress always free, reads far under the 10M/mo free Class B); AWS S3 ≈ $0.20/mo but has an egress tail risk ($0.09/GB — a viral burst could be a surprise bill), so avoid raw S3 unless CloudFront (1 TB/mo free) is in front. Signing with minisign/cosign keyless = $0 (one pinned keypair). Option B = $0 external but spends home-upload bandwidth and couples updates to backend uptime.

# What to build (programmatic implementation)

1. **Release pipeline (CI, GitHub Actions — free on public repo)**: on tag `runner-v*`, build runner binaries per platform (linux/darwin/windows × x64/arm64, e.g. Node SEA single executables), produce a `manifest.json` (version, per-asset sha256, release URL, min-compatible-backend), sign the manifest with minisign (or cosign keyless), and attach all artifacts + `manifest.json` + `manifest.json.minisig` to the GitHub Release. Mark canary releases as **pre-release**.
2. **Runner-side update check (pull, on idle)**: runner polls `GET https://api.github.com/repos/Ewrdad/Kainbain/releases/latest` (or `/releases` and pick by semver; skip pre-releases unless opted in) on a jittered interval and when idle between tasks. Compares `tag_name` to its own version; if newer, downloads the matching platform asset + manifest + signature.
3. **Verification before install (mandatory, runner-side)**: verify manifest signature against the **public key pinned in the runner binary** (never fetched from the network), then verify the downloaded asset's sha256 against the manifest. Abort on any mismatch and alert the backend. This keeps R05's runner-side enforcement property: the runner does not trust the backend OR the store blindly — only the pinned key.
4. **Self-update-on-idle**: only swap the binary when the runner has no active task (per MigrationPlan Phase 4 'Runner self-update-on-idle'); download to temp, verify, atomic rename, restart, re-register. Keep the previous binary for one version as a rollback (delete on next successful boot).
5. **Backend coordination (no code transfer)**: on `register`/`heartbeat` the runner reports its version; backend stores it, exposes the fleet version matrix in the Runners settings UI with an 'update available' badge, and **refuses task dispatch to runners below the minimum compatible version** (config knob, e.g. `KAINBAIN_RUNNER_MIN_VERSION`), returning 409 so the runner updates instead of mis-executing.
6. **Rollback**: point the 'latest' pointer back by re-tagging/marking the previous release as latest (GitHub: edit release / delete the bad one so `releases/latest` resolves to the prior tag), or pin `KAINBAIN_RUNNER_PINNED_VERSION` per runner. With R2, versioning is via object versions.
7. **Air-gapped/offline hosts**: support `KAINBAIN_RUNNER_UPDATE_URL` override so the manifest/assets can be mirrored from any S3-compatible store or internal HTTP server.

# Out of scope / rejected
- Backend serving or pushing runner code to runners (Option B) — rejected: maximizes R05 blast radius, couples updates to backend SPOF, costs backend bandwidth. Only niche: the default single-local-runner install can keep updating with the backend container as today; external runners must use the artifact channel.
- Raw AWS S3 without CloudFront — rejected on egress tail-risk/cost grounds for a hobby project.

# Acceptance criteria
- CI publishes a signed runner release on tag; runner on an old version picks it up on idle, verifies signature+sha256, updates, re-registers, and the fleet matrix shows the new version.
- Tampered asset or manifest fails verification and the runner keeps running the old version and alerts.
- Backend refuses dispatch to a below-min-version runner; after updating, dispatch resumes.
- Rollback to the previous release works by reverting the 'latest' pointer.
- Docs updated (PORTABLE_DEPLOYMENT.md / New Runner Onboarding flow) and an ADR added under `adr/`.
