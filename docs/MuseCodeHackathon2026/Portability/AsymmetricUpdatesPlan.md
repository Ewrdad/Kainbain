## A1. Goal, success criteria, non-goals

**Goal.** Split today's one lockstep deploy into three independently publishable and independently deployable components — `backend`, `frontend`, `runner` — versioned by the API contract each one publishes, so that a change which does not move a contract does not rebuild, re-push, or restart the other two. Separate *publish* (build + push images to Docker Hub + regenerate `dist/` for Runners; runs from the repo/pipeline) from *local deploy* (pull + restart on this homelab host; runs from `~/apps/kainbain/`).

**Success criteria (all must be demonstrably true at the end):**

1. A frontend-only change (e.g. a CSS tweak in `frontend/src/`) publishes **only** the frontend image, and `redeploy.sh --frontend` restarts **only** the frontend container; backend container ID and Runner processes are unchanged before/after.
2. A runner-only change (e.g. a new harness probe in `runner/`) regenerates **only** `dist/kainbain-runner-*.tar.gz` (+ manifest), pushes **no** image, and `redeploy.sh --runner` restarts **only** the Runner systemd units; both containers are unchanged.
3. A backend-only, contract-compatible change (patch/minor API bump or none) publishes only the backend image; frontend and Runner keep working against it with no redeploy and no version banner.
4. A contract-*breaking* change is caught **before** deploy: the compatibility check (WP-A2) fails the publish, and if forced through, the frontend banner / Runner registration error names the two incompatible versions instead of failing obscurely.
5. One real task run through the KainBain pipeline ends with its final stage green: the stage publishes (does not deploy), and the user then redeploys by hand with one command. No stage ever again fails with `./deploy.sh: not found`.
6. `~/apps/kainbain/` contains no source checkout and no homelab data has leaked into any published image, `dist/` artifact, or committed file ([MigrationPlan.md](MigrationPlan.md) §7 leak guard re-run).

**Non-goals (explicit — do not build these):** No GitHub Actions / external CI system. No Kubernetes, no registry other than Docker Hub, no image signing/SBOM work beyond what exists. No automatic semver bumping (a human edits the version; tooling only *checks*). No database for release state (files + registry tags are the state). No change to stage semantics, queue priority, harness behaviour, or the Runner protocol's wire shape except the additive version field in WP-A4. No containerising the Runner (it stays native, per §2).

## A3. Decisions (settled here — do not re-litigate while executing)

| ID | Decision | Rule (exact) | Rejected alternative |
|---|---|---|---|
| DA1 | One version file per component, owned by that component | `api/version.json`, `frontend/version.json`, `runner/version.json` (shapes in WP-A2). These are the *only* API-version sources. `package.json` `"version"` fields are untouched and meaningless | A single root `versions.json`: one edit would flag all three components in change detection and blur ownership |
| DA2 | Semver meaning | `MAJOR` = contract broke (a consumer on the old major must not be deployed against it); `MINOR` = contract grew backwards-compatibly; `PATCH` = no contract change at all. A human bumps it in the same change that changes the contract. Tooling never bumps, only reads and checks | Auto-bump from diff: contract breakage is a judgement call a path diff cannot make (F8/F9 show paths over- and under-approximate) |
| DA3 | Compatibility is a *range*, checked mechanically | Each consumer declares the provider range it accepts (e.g. `"backendApi": ">=1.0.0 <2.0.0"`). Compatibility ⇔ provider `apiVersion` satisfies every consumer range that will be co-deployed. Check uses the `semver` package already in both lockfiles as a transitive dep — WP-A2 promotes it to a direct dependency of `api` only, and the checker runs under `api`'s tree; no other new dependency | Keeping commit-equality (F2): that *is* the lockstep being removed. Hand-rolled semver comparison: a solved problem; do not reinvent it |
| DA4 | Change detection is a path table over `git diff`, nothing smarter | `scripts/detect-changed-components.mjs` maps changed paths → component set (table in WP-A3). Unknown paths flag **all three** (fail safe). Base defaults to the last published manifest's commit (`dist/release-manifest.json`), falling back to `HEAD~1`, overridable with `--base <ref>` / `KAINBAIN_PUBLISH_COMPONENTS=backend,frontend` | Content/API-surface analysis or a monorepo tool (Nx/Turbo/Bazel): re-inventing a mechanism the user explicitly said not to build |
| DA5 | Publish and deploy are different programs with different homes | **Publish:** new `publish.sh` at repo root (beside `deploy.sh`, so `./publish.sh` resolves the same way). Builds, tags, pushes, writes `dist/`. Never touches `~/apps/kainbain`, never restarts anything. **Deploy:** new `redeploy.sh` living in `~/apps/kainbain/` (template committed at `deploy/redeploy.sh`; installed once by hand). Pulls and restarts only. Never builds, never runs tests | Adding `--publish`/`--deploy` modes to the 1,497-line `deploy.sh`: keeps the fused monolith (F4) and its transient-unit/heartbeat machinery in the path of a 5-second frontend restart |
| DA6 | Image names and tags | `docker.io/<NAMESPACE>/kainbain-backend`, `…/kainbain-frontend`. Every publish pushes **two** tags: the immutable `<apiVersion>-<shortsha>` (e.g. `1.2.0-a1b2c3d`) and the moving `latest`. `<NAMESPACE>` comes from env `KAINBAIN_DOCKERHUB_NAMESPACE` at publish time; publish **fails closed** (exit 2, message naming the missing variable) when it is unset — it is never committed, defaulted, or guessed. The user sets it once; see CP-A3's stop-and-ask rule | Committing the namespace: it is an account identifier the user has not yet stated in the repo, and hardcoding it would strand every other installer (portability goal). Only pushing `latest`: no rollback target |
| DA7 | Per-component tags in prod | `docker-compose.prod.yml` gains `KAINBAIN_BACKEND_TAG` and `KAINBAIN_FRONTEND_TAG`, each falling back to the legacy `KAINBAIN_IMAGE_TAG`, then `latest`. This keeps today's single-tag `.env` working byte-for-byte until WP-A6 migrates it | Renaming outright: breaks the live `~/apps/kainbain/.env` (F3/F10) on first pull |
| DA8 | Runner distribution stays a tarball in `dist/` | `publish.sh --runner` runs the existing `scripts/package-runner.sh` (F1) and additionally stamps `runner/version.json`'s contents + the commit into the tarball as `runner/VERSION.json`, and records checksums in the manifest. Runners are not containerised and are not pushed to Docker Hub (native harness constraint, §2) | A Runner image: contradicts the standing "Runners stay native" assumption |
| DA9 | Deploy/publish commands are *host* commands, never Runner work | A `ci`/`script` stage whose command is a deploy/publish command (existing detection: `api/project/deployCommands.js` `isDeployCommand`, extended in WP-A1 to recognise `publish.sh`/`redeploy.sh`) must execute on the backend in the primary checkout — it must never be dispatched to a Runner, whose `runCiCommand` runs in a task worktree on `kb/<taskId>` (F6). This is the structural fix for F5 | Making `./deploy.sh` "work from any cwd": a full prod deploy from inside a task worktree on a task branch is wrong even when the file exists (the deploy-tree gate in `deploy.sh` exists precisely because of the build-581 stranded-branch incident) |
| DA10 | `deploy.sh` is frozen, then retired in place | During WP-A1–A5, `deploy.sh` is not edited except the fail-fast guard in WP-A1 step 3. Once WP-A7's end-to-end run is green, `deploy.sh --prod`'s staging/swap block is replaced by a printed pointer to `publish.sh` + `redeploy.sh` (WP-A7 step 4) — the file, its attempt-checkpoint/heartbeat machinery (`api/deployManager.js`, `api/continuity/deployReconcile.js` consumers), and `--rollback` stay working until then | Deleting `deploy.sh` early: `api/deployManager.js` spawns `./deploy.sh --prod`/`--rollback` and the continuity reconciler reads its checkpoints; ripping it out first breaks the very pipeline this plan is fixing |

## A4. The version contract (normative — WP-A2 implements exactly this)

**Files (new, committed):**

```json
// api/version.json — the backend is the provider for both consumers
{ "component": "backend", "apiVersion": "1.0.0",
  "accepts": { "frontend": ">=1.0.0 <2.0.0", "runner": ">=1.0.0 <2.0.0" } }

// frontend/version.json — the frontend is a consumer of the backend only
{ "component": "frontend", "apiVersion": "1.0.0",
  "requires": { "backendApi": ">=1.0.0 <2.0.0" } }

// runner/version.json — the runner is a consumer of the backend only
{ "component": "runner", "apiVersion": "1.0.0",
  "requires": { "backendApi": ">=1.0.0 <2.0.0" } }
```

Meanings, precisely:

- `apiVersion` = the contract *this component publishes or speaks*. Backend: its HTTP + `/ws` surface as consumed by the frontend, **and** its Runner protocol (`/runners/*`, `/tasks/:id/claim|claim-heartbeat|complete-execution`, dispatch) as consumed by Runners — one version for both surfaces for now; splitting them is a future MAJOR decision, not this plan's. Frontend: the backend-API shape it was built against (it publishes nothing; `apiVersion` records what it speaks). Runner: the backend protocol it speaks.
- **Wire compatibility (transitional, binding):** backend API `1.x` ≡ Runner protocol string `"v1"` (F7). WP-A4 maps them; a future backend `2.0.0` is where `"v2"` may appear. Until then `RUNNER_PROTOCOL` stays `"v1"` and register/heartbeat keep accepting exactly it — no Runner in the field breaks.
- **Who checks what, when:** (1) *Publish time* — `publish.sh` runs `node scripts/check-component-compat.mjs` which loads all three `version.json` files and fails if any `requires`/`accepts` pair is unsatisfiable by the versions *in the tree being published*. (2) *Deploy time* — `redeploy.sh` checks `~/apps/kainbain/release-manifest.json` with the same checker (WP-A6): when the checker is found and the recorded combination fails, it refuses to change anything; when no checker can be found it warns loudly and continues (deploy must not depend on a dev checkout). (3) *Run time* — backend `/status` publishes its `apiVersion` (WP-A4); the frontend banner and Runner register path compare ranges, not commits (WP-A4).
- **Bump discipline (human, reviewed in the diff):** contract-breaking ⇒ MAJOR +1 and widen consumers' ranges in the same change; additive ⇒ MINOR +1; otherwise PATCH +1 *or no bump* for pure internals — but if a component's code changed and is republished, its image/artifact tag still changes (tags carry the commit, DA6), so "no bump" never means "same artifact".

### WP-A3 — Change detection (no new mechanism)

1. Write `scripts/detect-changed-components.mjs`:

## A6. Risks, rollback, and compatibility summary

| Risk | Mitigation in this plan | Rollback |
|---|---|---|
| Incompatible frontend/backend pair deployed | Publish-time compat gate (WP-A5 2b), manifest check at deploy (WP-A6, warn-only by design), runtime banner naming both versions (WP-A4) | `./redeploy.sh --frontend --tag <prev>` / `--backend --tag <prev>` (immutable tags, DA6, make this always possible) |
| Runner speaks to a backend that dropped its protocol | API `1.x` ≡ wire `"v1"` frozen (A4); additive `versions.api` check never rejects old Runners (WP-A4 step 3) | `./redeploy.sh --runner` with the previous tarball (`runner.prev/` kept) |
| Change detection flags too little (a missed coupling) | Fail-safe table: `shared/**`, harness code, release machinery, and all unrecognised code flag extra components (WP-A3); `--all` always available | Republish with `./publish.sh --all`; no state to repair (manifest is derived) |
| Change detection flags too much (slow publishes) | Accepted cost; reasons are printed per component so the table can be tightened later with evidence | n/a |
| Docker Hub outage / no network at publish | Publish fails before any push (WP-A5 step 5); deployed system untouched (publish never deploys) | Nothing to roll back; retry publish |
| Homelab data leaking into public artifacts | A0 rule 7, CP-A5 leak check, §7 guard at CP-A7; images build only from the existing Dockerfiles' explicit `COPY` lists (F1) — executor must not add a `COPY . .` | Untag/delete the offending Hub tag (user, Docker Hub UI), republish clean |
| `deploy.sh` retirement breaking DeployManager/continuity | DA10 freeze-then-retire order; gutting is the *last* step and stops on any test break (WP-A7 step 4) | `git` revert of that single change restores the monolith; prod still runs on images + `redeploy.sh` meanwhile |

**Compatibility window (standing rule from go-live):** the backend supports the current and previous API MAJOR for Runners (when a `2.0.0` ever lands, `accepts.runner` becomes `>=1.0.0 <3.0.0` for one release), and the frontend is always redeployable against any backend inside its declared range. Anything outside a declared range is a publish-time failure, never a runtime surprise.

3. **Build number / changelog** — `deploy.sh` stamps `build.json` + bakes `changelog.json` today (F4/F12). This plan keeps `build.json` updated on backend redeploys (WP-A6) and drops changelog baking from the publish path (it was a deploy artifact, not a published one). If the user wants the changelog kept, it becomes a `publish.sh` step writing into `dist/` — a small, separate decision, not assumed here.
