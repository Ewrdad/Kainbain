# Question‑Me (Survey Generator)

Use this skill when you want an **agent stage** to produce a list of multiple‑choice questions (with an optional free‑form notes field) for a human to answer later. The skill:

1. **Generates questions** based on the stage’s prompt.
2. **Writes** a `{{outputFile}}` file in the current task’s directory (`docs/tasks/<taskId>/`).
3. **Never overwrites** existing content – it reads the file first and **appends** a new round of questions at the bottom, preserving any prior answers.
4. **Marks the stage as awaiting human input** (task status `waiting_human`) so the UI shows the survey banner and the survey page.
5. Supports **conditional questions** via one simple `showIf` object form: `{ "questionId": "q1", "value": "Option A" }` or `{ "questionId": "q1", "values": ["A", "B"] }`. The UI hides those questions unless the condition is met. No other condition syntax is supported — never write string expressions.
6. **Question ids must be unique across the whole survey** (including every appended round). Re-using an id makes answers ambiguous, so append rounds with fresh ids such as `q5`, `q6`.

## Expected `{{outputFile}}` format

The file contains a **machine‑parseable JSON block** wrapped in a fenced code block (`survey-json`). The JSON is the single source of truth; a human‑readable markdown preview is generated from it by the UI.

```markdown
# Survey – generated by the "question‑me" skill

```survey-json
{
  "round": 1,
  "generatedAt": "{{ISO_TIMESTAMP}}",
  "stage": "{{stageId}}",
  "questions": [
    {
      "id": "q1",
      "type": "single",
      "text": "What is the primary security concern?",
      "options": ["Authentication", "Authorization", "Data protection", "Other"],
      "required": true,
      "showIf": null
    },
    {
      "id": "q2",
      "type": "multiple",
      "text": "Which regulatory frameworks apply?",
      "options": ["PCI‑DSS", "HIPAA", "GDPR", "None"],
      "required": false,
      "showIf": { "questionId": "q1", "value": "Data protection" }
    }
  ],
  "answers": {
    "q1": { "selected": ["Data protection"], "notes": "PII in uploads" }
  }
}
```

*The UI renders each question as a set of radio‑buttons or check‑boxes with a **Notes** textarea underneath.*

When the user finishes the survey, the UI updates the `answers` object in‑place (preserving the surrounding JSON) and saves the file.

### Append‑only behaviour
- If `{{outputFile}}` already exists, the skill **reads** it, determines the next `round` number, and **appends** a new JSON block under a new heading `## Round N`.
- Existing `answers` objects are left untouched.
- The skill must never delete or rewrite previous rounds.

## How the engine treats the skill
- During stage execution, after the agent returns **success**, the backend inspects the stage’s skill list. If `question-me` is present, it reads `{{outputFile}}` and decides:
  - **Unanswered required questions** (or no `{{outputFile}}` at all) → the task parks with status `waiting_human` instead of auto‑advancing. The task detail page shows the survey banner; the survey page opens at `/tasks/:taskId/survey`.
  - **Explicitly empty round** (`questions: []` — you had good reason to ask nothing) → the run advances normally, no parking.
  - **Already answered** → the run advances normally.
- Submitting the survey (`POST /tasks/:taskId/survey`) merges answers only — questions are never added, removed, or renamed there. A partial save stays parked; a complete submit advances the task to its next stage, which may then read `{{outputFile}}`.

## Downstream stages
Tell the stage after the survey (e.g. the plan stage) to factor in `{{outputFile}}` — for example: "Factor in {{outputFile}} into your plan. If there is not enough information, fail the stage with information needed." A failback re-runs the question stage, which appends a fresh round at the bottom.

## Human‑only edge‑cases
- If you genuinely have **no questions**, still write one round with `questions: []` rather than writing no file. An empty round advances without parking; a missing file parks so a human confirms there is nothing to ask (the survey page offers Continue in both cases).

## UI considerations (mobile & desktop)
- Render each question inside a `<fieldset>`.
- Options are full‑width touch targets; use `type="radio"` for `single` and `type="checkbox"` for `multiple`.
- The **Notes** textarea is optional but always present; on mobile it expands to the full width.
- Conditional visibility is evaluated client‑side; hidden questions are collapsed but their stored answers remain unchanged.
- Accessibility: all inputs have `aria‑label` and are keyboard‑navigable.

## Configuring the output file

The output file name is read from the skill configuration. In `KB_config.json`:

```json
{
  "keywords": {
    "outputFile": { "value": "SURVEY.md" },
    "minQuestions": { "value": "0" }
  },
  "defaults": { "mode": "direct" }
}
```

A stage attachment can override the file name without editing the skill, for
example:

```json
{ "name": "question-me", "config": { "outputFile": "FEEDBACK.md" } }
```

Accepted config keys (canonical first, then aliases): `outputFile`, `surveyFile`,
`surveyFileName`, `fileName`, `targetFile`, `file`. Plain names without an
extension become a `.md` file (`FEEDBACK` → `FEEDBACK.md`); anything else must
already end in `.md`. Path traversal or unsafe names fall back to `SURVEY.md`.

Multi-stage tasks should give each question stage its own file, e.g.
`FEEDBACK.md`, `SECURITY_QUESTIONARY.md`, `INTENT_SURVEY.md`, while the
default single-survey setup keeps `SURVEY.md`.

## Suggested minimum question count

`minQuestions` is a soft prompt hint only; the engine never enforces it. A value
of `0` disables the suggestion.

## Minimal `KB_config.json`
The skill defaults to `SURVEY.md` and a disabled minimum, so an empty object is
still sufficient (`{}`).
